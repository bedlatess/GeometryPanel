# 0.1.2 寻车协议修复

用户在 0.1.1 实机确认登录、电量、预估续航、电压正常，但寻车没有鸣响。本次不读取用户账号、车辆响应或流量数据库，也不发送真实短信或车辆命令。

## 已确认的迁移遗漏

恢复网页 `inline-28.decoded.js` 的 `_0x13430c.search.steps`（字符偏移 59882–60013）返回两个连续步骤：先 POST `/v1.0/app/cfmotoserverapp/dbpoint/send`，再无请求体 PUT `/v1.0/app/cfmotoserverapp/vehicleInfo/control/{vin}`。0.1.1 仅迁移了第一步。接口目录来自 `inline-10.decoded.js:1454`。这证明实现遗漏，不是对该用户车辆后台状态的推断。

`_0x13430c.searchHigh.steps`（偏移 60072–60165）是独立 POST `/v1.0/app/cfmotoserverapp/vehicleInfo/controlV2`，请求体 `{param:"4",vin:<账号返回的车辆编号>}`。不作为普通寻车失败后的自动后备。

恢复网页 `inline-26.decoded.js` 的 `_0x49f4a8`（偏移 136264–139112）顺序执行步骤；每步必须满足 `ok && data !== false`，失败立即停止。0.1.1 只检查业务码，漏掉了布尔否定结果。现在两步都通过才提示完整流程提交；任一步失败、超时、取消或登录失效都不继续下发、不自动重试。

APK 的 `ActionActivity.smali:807–852` 也记录了第二次 PUT。但 JADX 常规输出将其显示为条件后备，简化输出和 smali 表明 PUT 在返回判断前调用；这里使用网页步骤与执行器作为网页迁移依据，不能把有歧义的反编译表达式当作最终控制流。

## 独立契约与回归

[recovered-horn-contract.json](recovered-horn-contract.json) 由本地工具读取恢复文件 AST、解释受限常量与对象表达式提取。没有执行旧脚本或其网络、DOM、反调试代码。记录源文件 SHA-256、偏移和合成车辆编号；测试将实际生成请求与该契约逐步比较，避免模拟服务与遗漏实现相互印证。

检查覆盖普通/高声寻车、空 PUT 的签名、车辆绑定、两步之间及 PUT 等待中的取消、布尔否定、拒绝、网络故障、登录失效、旧登录恢复、切车、离线和 PWA 更新。浏览器检查使用请求前模拟及本地 CSP，绝不发出真实车辆控制请求。

排查摘要只包含版本、时间、所选模式、步骤结果和数字协议错误码。不包含服务器原始 message、响应体、请求地址、手机号、token、UID 或车辆编号；记录只留当前页面内存，切车或退出清除。

部署来源的 PUT 与高声 POST 已做无凭据 OPTIONS 预检，允许 `https://bedlatess.github.io` 及所需请求头。预检不执行车辆命令，不能证明实际鸣响。

REA 静态分析引用：`ev_8f20bba299532b049849a4432b2b410ab92b1a17835546522d6ee8b90224e9f2`，输入是恢复 inline-28 的排版派生文件。解析成功，语义图因节点上限部分覆盖；上述步骤和执行器结论以限定范围的 AST 提取及 smali 交叉核对为依据，不声称全图完整或已观察到实车执行。

## 验收边界

完整自动检查通过并发布后，用户只需更新到 0.1.2，确认普通寻车是否鸣响；需要时可单独选择高声寻车。若车辆仍无响应，一次复制“查看寻车结果”的摘要即可定位失败步骤。车辆物理结果仍由用户实车验收。
