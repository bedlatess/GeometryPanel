# 预估续航显示 0：静态排查与修复

## 已确认的问题

当前模型把 `battery.hmiRidableMile` 放在 `home.hmiRidableMile` 前面，但恢复的旧版只有首页模型定义了这个续航字段。电池响应若碰巧包含同名的 0、占位值或其他形状，就可能覆盖主页的有效续航。

另一个独立问题是数值解析直接调用 `Number(value)`：`Number([])`、`Number([0])` 都等于 0。字段出现异常数组时，页面会把它当成有效的零续航；这也可能错误覆盖 SOC 或电压的有效回退值。

修改前，在本地合成数据上实际运行模型得到：

| 首页输入 | 电池输入 | 修改前输出 |
| --- | --- | --- |
| `hmiRidableMile: 64` | `hmiRidableMile: 0` | `0` |
| `hmiRidableMile: 64` | `hmiRidableMile: []` | `0` |
| `hmiRidableMile: []` | 接口不可用 | `0` |

这些是可复现的客户端缺陷，使用的是合成数据，不是用户真实响应。没有读取账号信息或发送真实请求，因此不能据此断言用户本次响应恰好属于其中哪一条路径。

提交 `31059af`（0.2.0）的 `src/core/model.ts` 差异只增加了日常数据，未更改原有续航优先级。因此这一取值缺陷此前已存在，不能仅凭用户在更新后观察到 0 就断言它由 0.2.0 新引入；真实触发条件仍未观测。

## 旧版证据

授权发布物：工作区 `analysis/zeehowebnext-1.8.12/web-published/inline-12.decoded.js`。

- 首页归一化函数 `_0x2457d7` 从第 2193 行开始；第 2195 行把 `response.data` 作为首页对象，第 2228 行明确映射 `range: numeric(home.hmiRidableMile, null)`。
- 第 1766 行把 IoT 属性 `HMIRidableMile` 描述为“剩余续航”，首页新鲜度列表第 1871–1874 行也把 `hmiRidableMile` 归到该属性。IoT 的名字用于数据来源/时间核对，本次没有把它另行推导成续航。
- 电池归一化函数 `_0x4c83f0` 位于第 2538–2583 行，只整理 SOC、电压、电流、功率、SOH、次数、温度等；没有读取或输出 `hmiRidableMile`。全文件搜索这个原始字段也只发现首页读取与其新鲜度描述。
- `maxRangeMileage` / `maxMileage` 在第 2229–2232 行单独映射为 `maxRange`，不是当前剩余续航。本修复没有用它乘 SOC，也没有套用示例或标称数据估算。

证据只证明旧客户端对首页字段的契约，不能证明服务端每一次响应的具体字段内容。

## 修复行为

1. 当前剩余续航只取 `home.hmiRidableMile`，与旧版一致。主页字段缺失/无效则显示未知；不再从没有恢复契约的电池同名字段补数。
2. 首页明确返回的 `0`、`"0"`、`"0.0"` 保持 0，不能用“非零优先”或阈值猜测覆盖它。
3. 数值只接受有限非负数字与十进制数字字符串，拒绝数组、对象、布尔值、空白、非数、负值和 Infinity。带单位文本、十六进制字符串也不当作接口读数。
4. SOC 保持电池优先、有效范围 0–100、四舍五入的既有行为；电压保持电池 `voltage`、电池 `bmsVoltage`、首页 `voltage`、首页 `bmsVoltage` 的既有优先级。两者都保留明确的有效 0。

修改文件仅 `src/core/model.ts`、`src/core/model.test.ts` 与本记录。未改登录、车辆控制、协议请求或页面布局。

## 验证及边界

`npx tsx --test src/core/model.test.ts`：11 项通过。回归涵盖主页有效续航不会被电池额外字段覆盖、主页真实 0 保留、主页缺失不拿电池猜测补数、数组/对象等不能变成 0、SOC 与电压有效回退及优先级保留。

尚未从静态证据确认的事项：用户当前主页是否实际上返回 0、缺失、异常形状或其他值，以及车型/后台是否改变了上报策略。若主页本身明确上报 0，修复后仍应显示 0；如果上报缺失/无效，应显示未知，不能伪造为正常续航。整批构建、浏览器模拟和真实 iPhone 验收由主任务统一记录。
